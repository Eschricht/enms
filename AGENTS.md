# AGENTS.md

Guidance for AI coding agents working in this repository.

## Package Manager

```bash
pnpm install
```

This is a **pnpm monorepo**. Always use `pnpm`, never npm or yarn.

## Build, Test, and Lint

```bash
pnpm lint                 # ESLint on all files
pnpm lint:fix             # ESLint auto-fix
pnpm test                 # Vitest (all workspace projects)
pnpm test -- --coverage   # With coverage (100% threshold enforced)
pnpm typecheck            # TypeScript across all packages
```

Filter to a specific package:

```bash
pnpm --filter @enms/demo dev
pnpm --filter @enms/layer-a dev         # Runs .playground (isolated layer dev)
pnpm --filter @enms/eslint-config test
```

> **Nuxt ESLint config**: Nuxt packages import `withNuxt()` from `.nuxt/eslint.config.mjs` — a file generated by `nuxt prepare`. The root `postinstall` script (`pnpm -r --if-present dev:prepare`) generates these directories after `pnpm install`, so lint works on a fresh clone. If you add a new Nuxt package that imports from `.nuxt/`, give it a `dev:prepare` script so `postinstall` covers it.

## Workspace Structure

```
enms/
├── apps/demo/           @enms/demo — Nuxt app (consumes layer)
├── packages/eslint-config/ @enms/eslint-config — Shared ESLint config
└── layers/layer-a/      @enms/layer-a — Reusable Nuxt layer
```

Workspace defined in `pnpm-workspace.yaml` via `packages: ['apps/*', 'packages/*', 'layers/*']`.

## Nuxt Layer Pattern

Layers are shareable Nuxt modules. Key rules:

1. **Layer entry point** is `nuxt.config.ts` — declared via `"main": "./nuxt.config.ts"` in `package.json`
2. **Isolated development** via `.playground/` — a mini Nuxt app that `extends` the layer. `pnpm dev` in a layer runs `nuxi dev .playground`
3. **Consumption** — apps use `extends: ['@enms/layer-a']` in their `nuxt.config.ts`
4. **App config augmentation** — layers declare typed config via `declare module '@nuxt/schema'` in `app/app.config.ts`. This gives consumers auto-completion when overriding values.

Example of app config augmentation in a layer:

```ts
// layers/*/app/app.config.ts
export default defineAppConfig({ myLayer: { name: 'default' } })

declare module '@nuxt/schema' {
  interface AppConfigInput {
    myLayer?: { name?: string }
  }
}
```

Consumers then override with full type safety:

```ts
// apps/*/app/app.config.ts
export default defineAppConfig({ myLayer: { name: 'Custom' } })
```

## Dependency Protocols

- **`workspace:*`** — for internal package references (e.g., `@enms/layer-a: workspace:*`)
- **`catalog:`** — for shared dependency versions centralized in `pnpm-workspace.yaml`
- Version bumps of cataloged deps should be done in `pnpm-workspace.yaml`, not individual `package.json`

## Testing

### Philosophy

- **Test your code, not third-party code.** Assume third-party packages (Vue, Nuxt, Vitest, `@nuxt/ui`) are well-tested and behave correctly. Tests should validate that your own code integrates correctly with those packages, not that the packages themselves work.
- **Focused tests.** Each test case should verify one specific behavior. Avoid bundling unrelated assertions into a single test.
- **Internal logic only.** Assert on your own output — rendered text, emitted events, returned values — not on framework internals like Vue's reactivity system or Nuxt's module resolution.

### File Structure

- Test files use the `*.spec.ts` naming convention
- Test file locations are determined by each vitest config's `include` patterns — place files where the config expects them
- Common conventions: Nuxt runtime tests (components, composables, pages) live in `test/nuxt/`, unit tests in `test/unit/` (apps/layers) or co-located with source (standalone packages), as reflected in each `vitest.{nuxt,unit}.config.ts`

### Choosing the Right Environment

Not every test needs the Nuxt runtime. Choosing the right environment keeps tests fast and focused.

| Environment | Config file             | Use when                                                                       | Example                                   |
| ----------- | ----------------------- | ------------------------------------------------------------------------------ | ----------------------------------------- |
| **Node**    | `vitest.unit.config.ts` | Testing plain TS/JS — utility functions, pure logic, data transformations      | `shared/utils/sum.ts`, `src/math.spec.ts` |
| **Nuxt**    | `vitest.nuxt.config.ts` | Testing code that depends on Nuxt — components, composables, pages, app config | `test/nuxt/hello-world.spec.ts`           |

Node tests are faster to set up and run since they skip Nuxt's module resolution, auto-imports, and build pipeline. If the code under test doesn't import from `#imports`, `#app`, or `.vue` files, prefer the node environment.

### Vitest Configuration

- **Workspace orchestration**: root `vitest.config.ts` discovers sub-project configs via `test.projects` glob patterns
- Each package has its own `vitest.config.ts` that delegates to `vitest.nuxt.config.ts` or `vitest.unit.config.ts`
- **100% coverage** enforced across lines, branches, functions, statements (`autoUpdate: true`)
- Coverage excludes: CSS files, playground dirs, and `app.config.ts` files

### Unit Test Patterns

- **Mock external dependencies** with `vi.mock` and `vi.hoisted` rather than relying on real implementations
- Use `vi.hoisted()` to hoist mock setup above imports, so mocks are in place before the module loads
- Test your wrapper's own behavior: option merging, default application, argument passthrough
- Do not re-test the internal behavior of the mocked dependency

```ts
// Example: mocking an external package to test a wrapper
const { externalFn } = vi.hoisted(() => ({
  externalFn: vi.fn(() => 'mocked'),
}))
vi.mock('external-package', () => ({ externalFn }))
```

### Nuxt Runtime Test Patterns

- Use `mountSuspended` from `@nuxt/test-utils/runtime` — it resolves Nuxt auto-imports and composables
- Use `defineVitestConfig` from `@nuxt/test-utils/config` in `vitest.nuxt.config.ts` with `environment: 'nuxt'`
- For layers, point `rootDir` at `.playground` so tests run against the isolated layer environment
- Use Nuxt auto-imports and aliases (`#components`, `~/`) to reference components — this is the idiomatic pattern for Nuxt runtime tests and matches [Nuxt's own testing docs](https://nuxt.com/docs/4.x/getting-started/testing). For layers where `rootDir` points to `.playground`, `~`/ aliases may not resolve files outside the playground — use relative imports for those cases (e.g., `import App from '../../app/app.vue'`). `#components` resolves correctly in both contexts.
- **Assert on rendered output**: text content (`wrapper.text()`), element existence (`wrapper.find()`), component presence (`wrapper.findComponent()`)
- Do not assert on Vue internals (reactive state, computed refs) or Nuxt UI component internals
- Take care not to mutate global state (plugins, composable state) between tests — the Nuxt environment initializes a shared global app

```ts
// Example: testing a component's rendered output
const wrapper = await mountSuspended(MyComponent)
expect(wrapper.find('h1').text()).toBe('Expected heading')
expect(wrapper.text()).toContain('Expected content')
```

#### `mockNuxtImport`

Use `mockNuxtImport` from `@nuxt/test-utils/runtime` to mock auto-imported Nuxt composables (e.g., `useState`, `useRoute`):

```ts
// Example: mocking useState in a test
import { mockNuxtImport } from '@nuxt/test-utils/runtime'

// Simple mock
mockNuxtImport('useState', () => {
  return () => ({ value: 'mocked value' })
})

// Typed mock with access to original implementation
mockNuxtImport<typeof useState>('useState', (original) => {
  return (...args) => {
    return { ...original('some-key'), value: 'mocked state' }
  }
})
```

<note>

`mockNuxtImport` can only be used once per mocked import per test file. It is a macro that gets transformed to `vi.mock` and is hoisted. Use `vi.hoisted` if you need different mock implementations between tests.

</note>

### What NOT to Test

- Vue reactivity internals (computed values, ref updates)
- Nuxt module resolution or auto-import behavior
- Third-party component internals (e.g., `@nuxt/ui` `UCard` rendering details)
- Framework lifecycle details (mount/unmount hooks)

## Commits

Conventional commits enforced via commitlint:

```
feat: add new feature
fix: resolve bug
chore: update dependencies
docs: update readme
refactor: restructure module
test: add coverage
```

Pre-commit hook runs `eslint --fix` on staged files via lint-staged.

## TypeScript

TypeScript 6 with strict mode. Nuxt packages use Nuxt's auto-generated tsconfig (`.nuxt/tsconfig.json`). The eslint-config package uses a standalone `tsconfig.json`.

## Code Style

- ESLint via `@enms/eslint-config` (wraps `@antfu/eslint-config` with `pnpm: true`, `formatters: true`)
- ESLint handles all formatting — **no Prettier**
- `eslint.config.ts` at each level imports and uses `enms()`
- Nuxt apps/layers compose with `withNuxt()` from `.nuxt/eslint.config.mjs`
